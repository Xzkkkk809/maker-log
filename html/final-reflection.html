// 05 · Reflections & Demo

反思 & 演示

从 MVP 到加入语音模块、防作弊判定的完整迭代反思，以及遇到的硬核 Bug 和解决过程。

迭代过程反思 / Iteration Insights
MVP · V1.0 → 发现问题
蜂鸣器提醒太生硬
最初版本只有蜂鸣器发出声响，测试时发现这个提醒方式很突兀，容易让人感到烦躁而不是被温和提醒。这让我们意识到"提醒"这件事本身也需要被设计——提醒的方式直接影响用户是否愿意接受它。
V1.5 → 加入正向反馈
绿灯闪烁记录喝水次数
原版只有"惩罚"没有"奖励"。加入绿灯闪烁记录喝水次数后，用户每次喝水都能看到今天喝了几次，产生了成就感。这个细节让整个交互从单向催促变成了双向反馈。
V2.0 → 最大升级
引入 ASR01 语音模块
加入语音播报"喝水吧"是整个项目最大的技术跨越。ASR01 通过串口与 ESP32 交互，需要调试波特率和触发指令格式。语音提醒比蜂鸣器更自然，更像一个关心你的助手，而不是一个在催你的闹钟。
V2.1 → 最有创意的细节
防作弊：3 秒判定机制
测试中发现用户可以只是把杯子拿起来立刻放回去就能"重置"提醒，完全绕过了喝水的目的。加入 3 秒判定后，必须真正拿起来喝水（超过 3 秒）才算有效。这个细节体现了"以用户行为为中心"的设计思考——不只是实现功能，还要考虑用户会如何"对付"这个功能。
Bug & 风险复盘（悬停翻转）
BUG 01
轻触开关被持续压坏
水杯长时间压在开关上，可能导致开关损坏，状态检测失误。
↗ 悬停查看解决方案
SOLUTION
备用按钮模拟
若开关故障，改用按钮手动模拟放杯/取杯动作，展示逻辑完全相同。
BUG 02
ASR01 串口调试困难
ASR01 模块与 ESP32 的串口通信波特率不匹配，导致语音无法正常触发。
↗ 悬停查看解决方案
SOLUTION
统一波特率 + 指令格式
调整双方波特率一致，确认 ASR01 触发指令格式后，语音播报稳定运行。
RISK
砍功能优先级
时间不足时应该先砍哪个功能，如何保证核心演示不受影响？
↗ 悬停查看方案
DECISION
核心 > 语音 > 防作弊 > 外观
先保证红绿灯提醒逻辑，再保语音，防作弊判定可简化，外观最后考虑。

总结与反思 / Reflection

这个项目最让我骄傲的地方，不是最终做出了什么，而是我们在两天内经历了四个版本的迭代——每一个版本的升级都来自于真实的测试反馈，而不是凭空想象。MVP 的蜂鸣器太吵、V1.5 的次数记录增加成就感、V2.0 的语音提醒更自然、V2.1 的防作弊判定最有创意，这条迭代链清晰地体现了设计思维中"测试→反馈→改进"的循环。

防作弊判定（3秒规则）是整个项目我最喜欢的细节。它源于一个很朴素的观察：如果一个装置能被人轻易"欺骗"，那它的核心价值就失去了。我们用3秒时间戳判断这次拿起杯子是真的喝水还是只是重置提醒，这个逻辑很简单，但背后体现了"以用户行为为中心"的设计思考。

整个学期最大的收获，是学会了在约束条件下快速迭代——时间有限、材料有限、技术能力有限，但只要方向对了，每一次小的改进都能让产品变得更好。
